## 0. 开场：项目定位与一句话卖点（1 分钟）

### 投影片标题
RAG 多模态电商导购 Agent 的端到端工程化闭环

### 讲解词

各位老师好。今天我答辩的项目是一个**面向电商导购场景的 RAG 多模态对话 Agent Demo**。它解决的核心问题是：当用户发来一条带图或不带图的购物咨询，比如"推荐一款 2000 元以内拍照好的手机"，系统如何在可预期的时间内完成**语义理解、商品检索、回答生成、卡片下发**，并以**流式 SSE** 返回给 Android 客户端。

与普通 LLM 聊天 Demo 不同，这个项目的重点不是"能聊天"，而是"**能上线**"——我们做了四层工程化设计：

1. **可离线运行**：默认零外部 LLM/向量库依赖，本地 fallback 即可 Demo；
2. **可防幻觉**：RAG 检索结果作为事实源，LLM 输出经 GroundingGuard 校验；
3. **可观测**：每次对话生成 Trace，/debug/traces 可查；
4. **可迭代**：JSONL 评估用例 + 首 Token/检索压测脚本，形成"改动→评估→压测"的闭环。

接下来我会从客户端开始，逐层走到后端，最后回到工程化闭环。

### 答辩技巧
- 专家如果问"为什么选电商导购？"：答需求高频、事实约束强、幻觉风险高，最能体现 RAG + Grounding 的价值。
- 专家如果问"和通用 ChatGPT 区别？"：答我们强调事实约束、商业事实增强、工程可观测，而不是开放域闲聊。

## 1. 全链路鸟瞰：一条请求怎么走完（2 分钟）

### 投影片标题
从用户开口到商品卡片上屏：一条请求的全链路

### 讲解词

先看整体数据流，后续每一节都会展开其中一个环节。

```text
Android Compose 用户输入
  → OkHttp SSE POST /chat
  → server/api/chat.py
  → Orchestrator.stream_chat()
       ├─ input_processor.process()      # 文本/图片
       ├─ semantic_planner.plan()        # 意图+过滤条件
       ├─ scope_transition + merge_filters
       └─ AgentTurnContext 构建
  → AgentWorkflow.stream(context)
       ├─ ClarificationHandler           # 澄清
       ├─ CartHandler                    # 购物车
       ├─ CompareHandler                 # 对比
       ├─ ScenarioBundleHandler          # 场景组合
       ├─ ContextFollowUpHandler         # 上下文追问
       └─ RecommendationHandler          # 兜底推荐
  → ToolRegistry.execute("search_products")
  → ProductRetrievalPipeline.run()
       ├─ VectorStore.query()            # 召回
       ├─ 7 个 post_processors           # 业务过滤
       ├─ dedupe_hits()                  # 去重
       └─ rerank_hits()                  # 重排
  → to_product_card() + commerce_gateway.enrich_product()
  → guard_grounded_answer()             # 防幻觉
  → SSE 流式下发：token → product_card → done
  → Android ViewModel 更新 → Compose 渲染
```

这条链路有两个关键设计：

1. **事件驱动**：每个阶段产出标准化事件（`status`/`token`/`product_card`/`cart_update`/`done`），前后端通过 SSE 事件名解耦。
2. **上下文对象 `AgentTurnContext`**：同一轮对话内，所有 Handler 和工具只读该对象，保证状态一致。

### 核心代码

事件封装在 `server/api/chat.py`：

```python
# server/api/chat.py
def sse(event: str, data: dict) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\ndata: {payload}\n\n"
```

整个编排器入口在 `server/agent/orchestrator.py`：

```python
# server/agent/orchestrator.py
async def stream_chat(self, session_id, user_message, ...):
    yield {"event": "status", "data": {"state": "thinking", "text": "正在思考"}}
    session = self.sessions.get(session_id)
    session.add_user_message(user_message)
    processed = self.input_processor.process(...)
    plan = await self.semantic_planner.plan(processed.text, session)
    # ... filters, scope_transition, context ...
    async for item in self.workflow.stream(context):
        yield item
```

### 答辩技巧
- 专家追问"为什么用 SSE 不用 WebSocket？"：答 SSE 对移动端更友好（基于 HTTP、自动重连简单、兼容 CDN/网关），且 `/chat` 以服务端推送为主，WebSocket 的双向优势不明显。
- 专家追问"请求超时怎么处理？"：答网关层 `/chat` 豁免外层超时，但内部每个阶段都有独立预算，后面会讲。

## 2. 客户端：SSE 流式渲染（3 分钟）

### 投影片标题
Android 客户端：OkHttp-SSE + Compose 状态机

### 讲解词

客户端是 Kotlin + Jetpack Compose，入口非常干净。`MainActivity.kt` 只做一件事：挂载主题和 `ChatRoute`。

```kotlin

        super.onCreate(savedInstanceState)
        setContent {
            RagShoppingAgentTheme {
                ChatRoute()
            }
        }
    }
}
```

真正的网络层在 `ChatSseClient.kt`。它用 OkHttp 的 `EventSource` 建立 SSE 长连接。注意这里 `readTimeout` 设为 0，因为 SSE 是持续推送的。

```kotlin
// client/.../network/ChatSseClient.kt
class ChatSseClient(
    private val baseUrl: String = BackendConfig.LOCAL_REVERSE_PROXY_BASE_URL,
) {
    private val client = OkHttpClient.Builder()
        .connectTimeout(15, TimeUnit.SECONDS)
        .readTimeout(0, TimeUnit.SECONDS)   // SSE 长连接不设置读超时
        .build()

    fun send(
        sessionId: String,
        message: String,
        onToken: (String) -> Unit,
        onProduct: (ProductCard) -> Unit,
        onComparison: (ComparisonCard) -> Unit,
        onCart: (CartState) -> Unit,
        onImageAnalysis: (String) -> Unit,
        onStatus: (String) -> Unit,
        onDone: () -> Unit,
        onError: (Throwable) -> Unit,
    ): EventSource {
        val body = JSONObject()
            .put("session_id", sessionId)
            .put("message", message)
            .toString()
            .toRequestBody("application/json; charset=utf-8".toMediaType())

        val request = Request.Builder()
            .url("$baseUrl/chat")
            .post(body)
            .build()

        return EventSources.createFactory(client).newEventSource(
            request,
            object : EventSourceListener() {
                override fun onEvent(
                    eventSource: EventSource,
                    id: String?,
                    type: String?,
                    data: String,
                ) {
                    val json = JSONObject(data)
                    when (type) {
                        "token" -> onToken(json.optString("text"))
                        "product_card" -> onProduct(ProductCard.fromJson(json))
                        "comparison_card" -> onComparison(ComparisonCard.fromJson(json))
                        "cart_update" -> onCart(CartState.fromJson(json))
                        "image_analysis" -> onImageAnalysis(json.optString("summary"))
                        "status" -> onStatus(json.optString("text"))
                        "done" -> onDone()
                    }
                }
            },
        )
    }
}
```

这里有两个关键点：

1. **事件名与 UI 回调一一对应**：后端新增事件类型时，前端只需要在 `when` 里加一个分支。
2. **每个事件都独立反序列化**：`ProductCard.fromJson`、`CartState.fromJson` 等，让 UI 层只关心自己需要的状态。

UI 状态由 `ChatViewModel` 管理。发送消息时，它先把用户消息和"思考中"的助手消息插入列表，再启动网络请求。

## 3. API 入口：协议转换与首屏反馈（2 分钟）

### 投影片标题
FastAPI 入口：从 HTTP 请求到 SSE 事件流

### 讲解词

后端是 FastAPI。`/chat` 路由是入口，它的职责很简单：**校验请求、注入依赖、把编排器事件包装成 SSE**。

```python
# server/api/chat.py
class ChatRequest(BaseModel):
    message: str | None = None
    session_id: str | None = None
    image_base64: str | None = None
    image_id: str | None = None
    image_mime_type: str | None = None
    image_filename: str | None = None

    @model_validator(mode="after")
    def require_message_or_image(self):
        if not self.message and not self.image_base64 and not self.image_id:
            raise ValueError("必须提供 message 或 image")
        return self
```

注意 `@model_validator`：它保证用户至少发了文字或图片之一，防止空请求进入编排器。

主路由用依赖注入拿到 `Orchestrator` 和 `Settings`，返回 `StreamingResponse`：

```python
# server/api/chat.py
@router.post("/chat")
async def chat(
    request: ChatRequest,
    orchestrator: Orchestrator = Depends(get_orchestrator),
    settings: Settings = Depends(get_settings),
) -> StreamingResponse:
    async def event_stream() -> AsyncIterator[str]:
        image_bytes, image_mime_type, image_filename = resolve_image_payload(request, settings)
        async for item in orchestrator.stream_chat(
            session_id=request.session_id,
            user_message=request.message,
            image_base64=request.image_base64,
            image_bytes=image_bytes,
            image_mime_type=image_mime_type,
            image_filename=image_filename,
        ):
            yield sse(item["event"], item["data"])

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

这里有两个工程化细节：

1. **依赖注入**：`Orchestrator` 是单例，由 `app_container.py` 装配，路由层不自己造对象。
2. **SSE 协议封装**：`sse()` 函数只负责把 `{"event": ..., "data": ...}` 转成标准 SSE 格式，与业务逻辑完全解耦。

```python
# server/api/chat.py
def sse(event: str, data: dict) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\ndata: {payload}\n\n"
```

### 答辩技巧
- 专家问"`resolve_image_payload` 做什么？"：答如果前端传了 `image_id`，后端从 `ImageUploadStore` 按 session 读取图片二进制；如果是 base64，直接解码。这样支持两种方式。
- 专家问"怎么防止图片太大？"：答上传接口有大小限制，`Settings` 中可配 `max_image_size_bytes`。

## 4. Orchestrator：一次对话的总控（3 分钟）

### 投影片标题
Orchestrator：会话状态、语义规划、上下文切换

### 讲解词

`Orchestrator` 是后端的大脑。它的 `stream_chat` 方法只做一件事：**按固定顺序推进一次对话，并在每个关键节点产出 SSE 事件**。

```python
# server/agent/orchestrator.py
async def stream_chat(self, session_id, user_message, ...):
    # 1. 立即告诉前端：我开始思考了
    yield {"event": "status", "data": {"state": "thinking", "text": "正在思考"}}

    # 2. 读取/创建会话
    session = self.sessions.get(session_id)
    session.add_user_message(user_message)

    # 3. 多模态输入处理
    processed = self.input_processor.process(
        text=user_message,
        image_base64=image_base64,
        image_bytes=image_bytes,
        ...
    )
    if processed.image_summary:
        yield {"event": "image_analysis", "data": {"summary": processed.image_summary}}

    # 4. 语义规划
    plan = await self.semantic_planner.plan(processed.text, session)

    # 5. 提取过滤条件并处理品类切换
    extracted = plan.to_filter_conditions()
    scope_transition = self.scope_transition_policy.decide(...)
    session.merge_filters(extracted, auto_scope_reset=scope_transition.should_reset)

    # 6. 构建本轮上下文对象
    context = AgentTurnContext(
        trace_id=trace_id,
        session_id=session_id,
        message=processed.text,
        intent=plan.to_user_intent(),
        query=plan.query or rewrite_query(processed.text, session),
        filters=SearchFilters.from_session(session),
        plan=plan,
        session=session,
        registry=self.registry,
        llm_client=self.llm_client,
        ...
    )

    # 7. 交给工作流，并把事件逐条 yield 出去
    async for item in self.workflow.stream(context):
        yield item

    # 8. 保存 trace 和 session
    trace_store.add(build_trace(...))
    sessions.save(session)
```

我重点讲三个设计决策：

**第一，首个事件是 `status:thinking`**。这在移动端非常重要，因为网络请求可能有几百毫秒延迟，如果没有首屏反馈，用户会觉得"卡住了"。我们让前端先显示"正在思考"，后面再有 token 和卡片。

**第二，`AgentTurnContext` 是不可变的上下文对象**。它包含本轮需要的全部信息：session、plan、filters、registry、llm_client。所有 Handler 和工具只读它，或在 `metadata` 里写诊断信息。这样避免同一轮内状态被意外修改。

```python
# server/agent/workflow.py
@dataclass
class AgentTurnContext:
    trace_id: str
    session_id: str
    message: str
    intent: UserIntent
    query: str
    filters: SearchFilters
    plan: SemanticPlan
    session: SessionState
    registry: ToolRegistry
    llm_client: LLMClient | None
    selected_handler: str = ""
    metadata: dict[str, Any] = field(default_factory=dict)
```

**第三，scope_transition 处理品类切换**。比如用户上一句问手机，这一句问眼霜，系统要自动清理手机的过滤条件，避免把"2000 元"带到眼霜检索里。

```python
# server/agent/scope_transition.py（概念示意）
scope_transition = self.scope_transition_policy.decide(
    current_message=processed.text,
    previous_filters=session.filters,
    plan=plan,
)
```

### 答辩技巧
- 专家问"为什么 Orchestrator 不直接处理业务，而要交给 Workflow？"：答职责分离。Orchestrator 负责"流程推进和状态管理"，Workflow/Handler 负责"业务动作"。新增业务只需要新增 Handler，不影响主流程。
- 专家问"会话状态都存什么？"：答 history、filters、candidate_products、cart、pending_subject 等，下一节会展开 session 持久化。

Orchestrator 把执行权交给 `AgentWorkflow`，它是一个轻量的 Handler 责任链。

## 5. Workflow + Handler：责任链路由（3 分钟）

### 投影片标题
AgentWorkflow：按意图分派的 Handler 责任链

### 讲解词

`AgentWorkflow` 的实现非常轻量：按顺序遍历 Handler，命中一个就执行，执行完就返回。

```python
# server/agent/workflow.py
class AgentWorkflow:
    def __init__(self, handlers: Sequence[AgentHandler]) -> None:
        self.handlers = list(handlers)

    async def stream(self, context: AgentTurnContext) -> AsyncIterator[dict]:
        for handler in self.handlers:
            if handler.matches(context):
                context.selected_handler = handler.__class__.__name__
                async for item in handler.handle(context):
                    yield item
                return
        raise RuntimeError("No agent handler matched the turn.")
```

关键是 `matches(context)`：每个 Handler 自己判断是否应该处理当前请求。

Handler 的注册顺序在 `default_handlers.py` 中：

```python
# server/agent/default_handlers.py
def build_default_workflow(scenario_catalog=None) -> AgentWorkflow:
    return AgentWorkflow(
        handlers=[
            ClarificationHandler(),      # 1. 意图不清时澄清
            CartHandler(),               # 2. 购物车操作
            CompareHandler(),            # 3. 商品对比
            ScenarioBundleHandler(...),  # 4. 场景组合方案
            ContextFollowUpHandler(),    # 5. 上下文商品详情追问
            RecommendationHandler(),     # 6. 兜底推荐
        ]
    )
```

这个顺序是有讲究的：

1. **ClarificationHandler** 放最前：如果用户需求太宽泛（"推荐一款手机"），先追问预算/偏好，不硬推商品。
2. **CartHandler** 第二："加购""删除"这类动作要优先处理，不能让用户说完购物车操作后系统还去推荐。
3. **CompareHandler** 第三："A 和 B 哪个好"直接进对比，不走普通推荐。
4. **ScenarioBundleHandler** 第四："我要去三亚度假"这种跨类目组合需求。
5. **ContextFollowUpHandler** 第五："第二个怎么样""那个适合干皮吗"这类上下文追问。
6. **RecommendationHandler** 兜底：前面都不命中时做普通推荐，它的 `matches` 直接返回 `True`。

```python
# server/agent/recommendation_handler.py
class RecommendationHandler(AgentHandler):
    def matches(self, context: AgentTurnContext) -> bool:
        return True  # 兜底
```

### 答辩技巧
- 专家问"Handler 之间会不会重复命中？"：答不会，责任链命中一个就 `return`，后面的 Handler 不会执行。
- 专家问"如果两个 Handler 都能匹配怎么办？"：答通过顺序解决优先级。例如"加购"和"推荐"可能都含商品词，但购物车动作语义更强，所以放前面。

### 承上启下
最常见的路径是 RecommendationHandler。它内部要调用检索、生成、卡片绑定、防幻觉。接下来详细讲。

## 6. RecommendationHandler：检索、生成、卡片绑定（4 分钟）

### 投影片标题
推荐 Handler：检索 → 生成 → Grounding → 卡片输出

### 讲解词

`RecommendationHandler` 是普通推荐路径的核心。我把它拆成四步。

**第一步，带预算的检索。**

```python
# server/agent/recommendation_handler.py
async def handle(self, context: AgentTurnContext) -> AsyncIterator[dict]:
    product_search = context.registry.get("search_products")
    discovery_policy = build_product_discovery_policy(context.plan)

    search_execution = await execute_product_search_with_budget(
        product_search=product_search,
        query=context.query,
        filters=context.filters,
        top_k=discovery_policy.top_k,
        timeout_seconds=context.retrieval_timeout_seconds,
    )

    cards = search_execution.cards
    if search_execution.diagnostics:
        context.metadata["retrieval"] = asdict(search_execution.diagnostics)
```

这里的关键是 `execute_product_search_with_budget`：检索有独立超时，超时后不会阻塞，而是返回空卡片并标记 `degraded`，系统会优雅降级。

**第二步，空泛请求抑制。**

如果用户没有给出类目、品牌、商品类型等结构化约束，我们不乱放卡片：

```python
# server/agent/recommendation_handler.py
if should_suppress_unscoped_product_cards(context):
    context.metadata["catalog_gap"] = {
        "reason": "缺少结构化约束，抑制商品卡片",
        "query": context.query,
    }
    cards = []
```

这是为了避免"我要买东西"这种空泛请求直接返回无关商品。系统会生成一段澄清或建议性文字，但不附带卡片。

**第三步，回答生成与 Grounding。**

先基于卡片生成 `fallback_answer`，再尝试 LLM 回答，但 LLM 输出必须经过 `guard_grounded_answer`：

```python
# server/agent/recommendation_handler.py

llm_answer = await collect_llm_answer_with_budget(context, cards)

    guarded = guard_grounded_answer(
        answer=clean_answer_text(llm_answer),
        cards=cards,
        fallback_answer=fallback_answer,
        allowed_extra_prices=[...],
    )
    if not guarded.safe:
        yield {
            "event": "guardrail",
            "data": {"action": guarded.action, "violations": guarded.violations},
        }
    answer = guarded.answer
else:
    answer = fallback_answer
```

如果 GroundingGuard 发现 LLM 说了不该说的（比如未提供的优惠、候选商品里没有的价格），会触发 `guardrail` 事件并回退到 grounded fallback。

**第四步，卡片绑定与输出。**

```python
# server/agent/recommendation_handler.py
resolved = resolve_product_cards_for_answer(answer, cards)
async for item in stream_text(answer):
    yield item
for card in resolved.cards:
    yield {"event": "product_card", "data": card}
yield {"event": "done", "data": build_done_payload(context, resolved)}
```

`resolve_product_cards_for_answer` 会根据回答中提到的品牌/名称重新排序并绑定卡片，确保"嘴上说的人和卡片一致"。随后先流式输出文字 token，再逐个下发商品卡片，最后发 `done`。

### 答辩技巧
- 专家问"为什么先文字后卡片？"：答文字是解释，卡片是证据。用户先看到"基于检索结果，我推荐以下 3 款"，再看到卡片，体验更自然；同时 token 流可以更快首屏。
- 专家问"`presentation_mode` 是什么？"：答 plan 里有 `single`/`listing`/`auto` 三种模式，决定召回 top_k 和展示风格。比如"我要最便宜的一款"用 `single`。

## 7. RAG 检索 Pipeline：从 Query 到候选商品（4 分钟）

### 投影片标题
ProductRetrievalPipeline：召回 → 过滤 → 去重 → 重排

### 讲解词

检索流水线在 `server/rag/retrieval_pipeline.py`。它的设计目标是：**既有向量召回的语义泛化能力，又有业务规则的安全兜底**。

```python
# server/rag/retrieval_pipeline.py
class ProductRetrievalPipeline:
    def __init__(self, store: VectorStore, *, candidate_multiplier=10, min_candidate_pool=50):
        self.store = store
        self.candidate_multiplier = max(candidate_multiplier, 1)
        self.min_candidate_pool = max(min_candidate_pool, 1)
        self.post_processors = [
            RangeFilter(),         # 价格区间
            ProductTypeFilter(),   # 商品类型
            CategoryFilter(),      # 类目
            BrandFilter(),         # 品牌
            StockFilter(),         # 有货
            KeywordFilter(),       # 关键词
            ExclusionFilter(),     # 排除属性
        ]
```

`run()` 方法体现了完整五步：

```python
# server/rag/retrieval_pipeline.py
def run(self, query: str, filters: SearchFilters, top_k: int = 5) -> RetrievalPipelineResult:
    candidate_top_k = max(top_k * self.candidate_multiplier, self.min_candidate_pool)
    steps: list[RetrievalStep] = []

    # ① Store 预过滤召回
    hits = self.store.query(query, top_k=candidate_top_k, filters=filters)
    steps.append(RetrievalStep("store_prefilter_recall", len(hits), ...))

    # ② 若带过滤无结果，回退到无预过滤召回
    if not hits and (filters.product_types or filters.categories):
        hits = self.store.query(query, top_k=candidate_top_k, filters=VectorSearchFilters())
        steps.append(RetrievalStep("store_recall_without_type_prefilter", len(hits), ...))

    # ③ 后处理过滤
    for processor in self.post_processors:
        hits = processor.apply(hits, filters)
        steps.append(RetrievalStep(processor.__class__.__name__, len(hits), ...))

    # ④ 去重 + 重排
    hits = dedupe_hits(hits)
    hits = rerank_hits(hits, query=query, filters=filters)

    # ⑤ 截断返回
    return RetrievalPipelineResult(hits=hits[:top_k], diagnostics=RetrievalDiagnostics(steps=steps))
```

我重点解释两个工程化设计。

**第一，本地 fallback 与 Chroma 的互补。**

默认配置 `USE_CHROMA=false`，系统使用 `LocalJsonVectorStore`，不需要外部向量数据库：

```python
# server/rag/stores.py
class LocalJsonVectorStore:
    def query(self, query: str, top_k=5, filters=None) -> list[dict]:
        query_tokens = tokenize(query)
        hits = []
        for doc in self.candidate_documents(filters):
            score = score_document_features(query_tokens, self.document_features[doc.id])
            if score > 0:
                hits.append({"id": doc.id, "text": doc.text, "metadata": doc.metadata, "score": score})
        return heapq.nlargest(top_k, hits, key=lambda item: item["score"])
```

它基于 token 重叠、类目倒排索引、文档特征缓存做快速召回，适合 Demo 和本地开发。

当 `USE_CHROMA=true` 时，使用 ChromaDB，并把业务过滤下推到 `where` 子句：

```python
# server/rag/chroma_metadata.py
def build_chroma_where(filters):
    clauses = []
    if filters.min_price is not None:
        clauses.append({"price": {"$gte": float(filters.min_price)}})
    if filters.max_price is not None:
        clauses.append({"price": {"$lte": float(filters.max_price)}})
    if filters.in_stock_only:
        clauses.append({"stock": {"$gt": 0}})
    if filters.categories:
        category_clauses = [{category_filter_key(c): True} for c in filters.categories]
        clauses.append({"$or": category_clauses} if len(category_clauses) > 1 else category_clauses[0])
    return {"$and": clauses} if len(clauses) > 1 else clauses[0] if clauses else None
```

**第二，rerank 把业务意图显式注入排序。**

```python
# server/rag/retrieval_pipeline.py
def relevance_bonus(metadata, *, query, filters) -> float:
    bonus = 0.0
    if filters.product_types and any(product_type_matches(item, metadata) for item in filters.product_types):
        bonus += 20.0
    if filters.categories and any(category_matches(item, metadata) for item in filters.categories):
        bonus += 12.0
    for keyword in filters.keywords:
        if keyword and keyword.lower() in haystack:
            bonus += 6.0
    for brand in filters.preferred_brands:
        if brand and brand.lower() in str(metadata.get("brand", "")).lower():
            bonus += 5.0
    return bonus
```

加分项把类目、商品类型、关键词、品牌等业务意图显式注入排序，弥补纯向量/字面匹配的不足。

### 答辩技巧
- 专家问"为什么本地 fallback 还能召回？"：答电商 query 通常含明确品牌/型号/类目词，token 重叠 + 倒排索引已经能召回大部分结果；语义泛化靠 Chroma + Ark embedding 增强。
- 专家问"candidate_multiplier 10 会不会太大？"：答这是召回池，后面会经过 7 层过滤和 top_k 截断，10 倍是为了在过滤后仍有足够候选。

## 9. GroundingGuard：生成后的事实闸门（3 分钟）

### 投影片标题
GroundingGuard：拦截价格、优惠、库存、绝对化用语的幻觉

### 讲解词

`GroundingGuard` 是生成后的一道规则化事实闸门。它的输入是 LLM 回答和商品卡片，输出是"安全通过"或"回退到 grounded fallback"。

```python
# server/agent/grounding.py
@dataclass(frozen=True)
class GroundingResult:
    answer: str
    safe: bool
    violations: list[str] = field(default_factory=list)
    action: str = "pass"
    citations: list[dict] = field(default_factory=list)

def guard_grounded_answer(*, answer, cards, fallback_answer, allowed_extra_prices=None):
    violations = detect_grounding_violations(answer=answer, cards=cards, allowed_extra_prices=allowed_extra_prices or [])
    if not violations:
        return GroundingResult(answer=answer, safe=True, citations=build_answer_citations(answer, cards))
    return GroundingResult(
        answer=fallback_answer,
        safe=False,
        violations=violations,
        action="fallback",
        citations=build_answer_citations(fallback_answer, cards),
    )
```

`detect_grounding_violations` 拦截 5 大类幻觉：

```python
# server/agent/grounding.py
def detect_grounding_violations(*, answer, cards, allowed_extra_prices):
    violations = []

    # 1. 未提供的优惠
    matched = terms_in_text(answer, PROMOTION_TERMS)
    if matched:
        violations.append(f"unsupported_promotion_terms:{','.join(matched)}")

    # 2. 未提供的商业数据（库存、销量、好评率）
    matched = terms_in_text(answer, UNSUPPORTED_BUSINESS_TERMS)
    if matched:
        violations.append(f"unsupported_business_terms:{','.join(matched)}")

    # 3. 绝对化/医疗化宣称
    matched = terms_in_text(answer, ABSOLUTE_OR_MEDICAL_CLAIMS)
    if matched:
        violations.append(f"unsupported_absolute_or_medical_claims:{','.join(matched)}")

    # 4. 未 grounded 的价格
    unsupported = prices_not_grounded(answer, cards, allowed_extra_prices)
    if unsupported:
        violations.append(f"unsupported_prices:{','.join(unsupported)}")

    # 5. 有卡片但未引用任何候选
    if cards and not references_any_candidate(answer, cards) and not answer_declines_product_recommendation(answer):
        violations.append("missing_candidate_reference")

    return violations
```

我重点讲价格校验。用正则抽出回答里的价格，再和商品卡片允许的价格集合比对：

```python
# server/agent/grounding.py
PRICE_PATTERN = re.compile(r"(?:[¥￥]\s*(\d+(?:\.\d+)?)|(\d+(?:\.\d+)?)\s*元)")

def prices_not_grounded(answer, cards, allowed_extra_prices):
    allowed = {normalize_price(candidate_fact(card, "price", 0)) for card in cards}
    allowed.update(normalize_price(v) for v in allowed_extra_prices)
    unsupported = []
    for match in PRICE_PATTERN.finditer(answer):
        raw = match.group(1) or match.group(2) or ""
        if normalize_price(raw) not in allowed:
            unsupported.append(raw)
    return unsupported
```

引用溯源则记录回答中引用了哪些商品字段：

```python
# server/agent/grounding.py
```

### 答辩技巧
- 专家问"规则化 Guard 会不会太僵硬？"：答目前是兜底安全网，复杂场景可以结合 LLM-as-judge 做二级校验；但规则响应快、可解释、零成本，适合生产第一防线。
- 专家问"如果 LLM 就是不说价格，只说"性价比高"怎么办？"：答"性价比高"是相对性描述，不在关键词表里，但会触发 `missing_candidate_reference` 如果它完全不提商品名；我们更严格控制的是"具体数字/优惠/库存"这类事实性幻觉。

### 承上启下

## 10. 语义规划：规则为主、LLM 为辅（2 分钟）

### 投影片标题
SemanticPlanner：规则兜底 + LLM 增强的混合规划

### 讲解词

语义规划器决定"用户想要什么"。它的设计原则是：**规则保证低延迟和稳定性，LLM 负责复杂长句的增强理解**。

`SemanticPlanner` 在 `server/agent/semantic_llm.py`：

```python
# server/agent/semantic_llm.py
async def plan(self, message: str, session: SessionState) -> SemanticPlan:
    fallback = build_rule_plan(message, session)          # 1. 规则兜底
    if not should_try_llm_planning(message=message, fallback=fallback, session=session):
        return fallback                                   # 2. 简单/高置信直接返回
    llm_plan = await self._try_llm_plan(message, session) # 3. 尝试 LLM 规划
    if llm_plan is None:
        return fallback
    merged = merge_semantic_plans(fallback=fallback, llm_plan=llm_plan)
    return validate_semantic_plan(merged)
```

规则 planner 在 `semantic_rules.py`：

关键设计：

1. **规则覆盖常见电商意图**：类目、品牌、价格、库存、facet（内存/颜色/鞋码）、指代、购物车动作。
2. **LLM 只增强复杂句**：`should_try_llm_planning` 判断是否需要 LLM；LLM 超时 0.8 秒，失败就回规则。
3. **merge 时高风险意图强制用规则**：`cart/compare/bundle` 这类涉及写操作或高风险的意图，merge 时优先采用规则结果，避免 LLM 乱解析。

### 答辩技巧
- 专家问"为什么不直接全用 LLM 规划？"：答电商意图大多结构化，规则又快又稳；LLM 有延迟和不确定性，且成本高。混合方案兼顾体验与成本。
- 专家问"规则覆盖不了新说法怎么办？"：答 taxonomy 支持别名、复合词、拼写容错；同时 `product_taxonomy.json` 和 `brand_aliases.json` 是独立配置文件，运营可维护。

### 承上启下
语义规划是"理解用户"，RAG 检索和 Grounding 是"基于事实回答"。但一个能上线的系统不止这些，还需要配置管理、会话持久化、限流熔断、评估、压测、Trace——也就是工程化闭环。

#### 11.3 网关韧性：限流、超时、重试、熔断

`RequestGovernanceMiddleware` 在 ASGI 层控制并发：

```python
# server/gateway/middleware.py
class RequestGovernanceMiddleware:
    def __init__(self, app, *, max_concurrent_requests=100, request_timeout_seconds=30.0,
                 timeout_exempt_paths=("/chat", "/ws/chat")):
        ...

    async def __call__(self, scope, receive, send):
        acquired = await self._try_acquire()
        if not acquired:
            await self._reject(scope, send)   # 503 server_busy
            return
        try:
            if self._should_apply_timeout(scope):
                await asyncio.wait_for(self.app(scope, receive, send), timeout=...)
            else:
                await self.app(scope, receive, send)
        except TimeoutError:
            await self._send_timeout(scope, send)  # 504 request_timeout
        finally:
            await self._release()
```

`/chat` 被豁免外层超时，因为 SSE 流式响应可能持续几十秒；但内部 LLM/检索调用有独立预算和重试熔断：

```python
# server/llm/ark_client.py
async def stream_messages(self, messages: list[dict]) -> AsyncIterator[str]:
    for attempt in range(1, attempts + 1):
        await self.circuit_breaker.before_call()
        try:
            async for token in self._stream_messages_once(messages):
                yield token
            await self.circuit_breaker.record_success()
            return
        except Exception as exc:
            await self.circuit_breaker.record_failure()
            if not is_retryable_llm_error(exc) or attempt >= attempts:
                raise
            await asyncio.sleep(self.retry_policy.delay_for_attempt(attempt))
```

## 12. 收尾：设计思想与扩展性（1 分钟）

### 投影片标题
三层解耦、事件驱动、可替换、可扩展

### 讲解词

回顾整个项目，它的核心架构思想可以概括为四点：

1. **三层解耦**：API 层只负责协议转换，Orchestrator 负责状态与规划，Workflow/Handler 负责业务动作，Tools 负责领域能力。每一层只依赖下一层的接口。
2. **事件驱动**：前后端通过标准化 SSE 事件通信，新增事件类型只需两端各自扩展。
3. **可替换**：向量存储、会话存储、LLM、商业事实服务都是接口化设计，`.env` 一个开关即可切换实现。
4. **可观测**：Trace 记录每次对话全链路，评估/压测脚本量化正确性与性能，形成"改动→验证→优化"的闭环。

未来扩展方向也很自然：接入订单查询 Handler、接入语音输入、接入真实电商价格/库存 API、用 LLM-as-judge 增强 GroundingGuard。

## 附录 A：专家高频追问与应对话术

### Q1：你们这和直接用 ChatGPT 做推荐有什么区别？

**答**：ChatGPT 是开放域生成，容易编造价格、库存、优惠信息；我们是 RAG + 商业事实增强 + GroundingGuard，所有价格/库存来自商品 catalog 或商业事实 gateway，回答必须引用候选商品。并且我们有评估、压测、Trace 的工程化闭环。

### Q2：为什么用规则做语义规划，不用大模型端到端？

**答**：电商意图大多结构化，规则又快又稳、可解释、零成本；LLM 作为复杂长句的增强。混合方案延迟可控，且购物车/对比等高风险意图强制用规则，避免 LLM 不稳定导致误操作。

### Q3：本地 fallback 的检索质量会不会很差？

**答**：电商 query 通常含明确品牌/型号/类目词，token 重叠 + taxonomy 归一化已经能召回大部分结果。Chroma + Ark embedding 提供语义泛化能力，但本地 fallback 保证零外部依赖时也能 Demo。

### Q4：GroundingGuard 的规则会不会太僵硬？

**答**：GroundingGuard 是第一道防线，拦截的是事实性风险（价格、优惠、库存、销量、绝对化/医疗用语）。更复杂的语义风险可以后续叠加 LLM-as-judge 做二级校验。规则的优势是快、可解释、零成本。

### Q5：多模态图片找货怎么实现的？

**答**：默认用 12×12 RGB 视觉签名做相似匹配，可选 Ark 多模态 embedding。图片理解后会生成 `image_summary` 和 `visual_matches`，拼入 query 后走同一套 RAG 链路。前端通过 `image_analysis` 事件展示图片理解结果。

### Q6：会话持久化为什么支持三种后端？

**答**：为了覆盖不同部署阶段。memory 适合开发调试；sqlite 是默认推荐，零运维；redis 支持多实例共享会话。三者接口统一，`.env` 切换即可。

### Q7：压测指标为什么看"首 token"而不是接口 RT？

**答**：因为用户感知的是"什么时候开始看到内容"。SSE 流式响应下，接口 RT 可能包含整个生成过程，但首 token、首商品卡片才是真实用户体验指标。

### Q8：如果真实接入价格/库存服务，改动大吗？

**答**：不大。只需实现 `CommerceServices` 里的 `PricingService`、`InventoryService` 等接口，在 `app_container.py` 替换 gateway 实现即可。Handler、RAG、Grounding 都不需要改。
